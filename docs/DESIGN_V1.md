## 0. 一页执行摘要

**一句话产品：** 用户画出一个闭合轮廓，EarthGlyph 从开放地图数据里寻找相似形状的真实湖泊、水库和池塘，展示实际地理位置、轮廓叠加，并生成可分享链接与图片。

**原则：** 真搜索，非预设匹配；不把纯轮廓检索称为卫星影像 AI 检索；不人为制造相似度百分比；不需要在网站运行大模型。先完成真实数据 PoC，再实现网站。

**本次比赛目标 V1：** 自由描画 → 检索真实地物 → 查看前 10 个候选 → 地图定位与旋转叠加 → 保存/分享。前端采用静态优先方案，降低 Qoder Sites 额度依赖。

**本次不做：** 任意线条/汉字/猫形跨模态检索、全球卫星照片抓取、AI 聊天、账号体系、点赞榜、自动扩展到道路/岛屿、训练遥感模型。

**开工门槛：** 先验证真实地貌候选库确实包含足够多有趣的可检索形状，及匹配算法对人工草图的效果；不可只用合成轮廓当作成功证据。

## 1. 用户、场景和完成标准

### 1.1 使用者
- 普通地图/地理爱好者：随手画轮廓，寻找真实景观。
- 社交媒体创作者：制作“你画的图案在地球上出现了”的内容。
- 教学或科普用户：探索自然与人工水体的多样形态。

### 1.2 核心流程（5 步）
1. 打开网站，看到绘图画布与 3 个经过真实搜索验证的示例草图。
2. 用鼠标或触控画封闭轮廓；支持清空、撤销、自动闭合。
3. 点击“搜索地球”，筛选并显示真实地图数据库中的候选结果。
4. 点击结果，展示地图位置、真实水体轮廓和草图叠加；可切换旋转/镜像匹配。
5. 分享包含查询草图和候选地物 ID 的 URL，或导出自制 SVG/PNG 发现卡片。

### 1.3 不可妥协的要求
- 每个搜索结果必须有真实地理几何、坐标、来源 ID、数据版本；不允许随机生成结果。
- 明确标注“当前搜索覆盖的数据集/地区/地物类型”；不能宣称是全球全部卫星图像。
- 对结果较差的草图直接展示“当前图库未找到特别接近的形状”，允许重新编辑。
- 不虚构水体名称；没名称就用地物类型和附近大致区域或坐标展示。
- 搜索结果必须可以在地图上打开，不能只显示形状缩略图。
- 地图底图与原始数据均展示正确的署名和许可。

## 2. 数据与许可

### 2.1 官方首选：Overture Maps Base / Water
官方 Schema：`https://docs.overturemaps.org/schema/reference/base/water/`

字段重点：`id`, `geometry`, `subtype`, `class`, `names`, `bbox`, `sources`。

**注意：** `geometry` 可能是 Point / LineString / Polygon / MultiPolygon，不是所有 `water` 都能直接当作闭合轮廓。首版仅收 Polygon/MultiPolygon，并限定 `subtype` 为 `lake`, `pond`, `reservoir`（`water` 只有经检查后才加入）。排除 `ocean`, `physical`, 线要素和任意地图瓦片边界片段。不要将“湖中岛屿的内环”与外边界混在一起。

官方 Python 下载工具：`https://docs.overturemaps.org/getting-data/overturemaps-py/`

```bash
python -m venv .venv
# Windows PowerShell: .\.venv\Scripts\Activate.ps1
# Linux/WSL: source .venv/bin/activate
pip install overturemaps geopandas shapely pyproj numpy scipy opencv-python-headless duckdb pyarrow pytest matplotlib

# 测试下载：美国威斯康星州部分湖泊区，bbox 顺序：西、南、东、北
# bbox 为样例，实际可换芬兰南部等地区
mkdir -p data/raw

overturemaps download \
  --bbox=-90,44,-89,45 \
  --type=water \
  -f geoparquet \
  -o data/raw/wisconsin_water.parquet
```

先在小区域验证 Schema、数据大小与候选数，再扩大下载范围，不要一次下载全球。

### 2.2 替代来源
- Geofabrik：按区域提供 OSM PBF；若 Overture 字段/提取不理想，可转用 Osmium / PyOsmium。
- Natural Earth：仅适合作为少量全球地理形状示例，精度不足以代替湖泊数据主体。
- NAIP / Sentinel：V3 的真实遥感影像数据；V1 不引入。

### 2.3 法律与数据边界
- Overture Base Water 主要源于 OSM，受 ODbL 等适用许可约束；显示来源署名，保留数据版本、来源、许可说明，若公开分发衍生数据库需核查 ODbL 的共享要求。
- 地图底图选允许该访问模式的瓦片供应商，开发期可用合理限流的底图；不要把 OSM 官方公共瓦片批量下载成搜索数据。
- 不要批量下载或自动分析 Google Maps / Google Satellite 瓦片；其政策禁止此类非可视化用途。
- SVG 分享卡片可以只画自有草图、开放矢量轮廓及文字，避免不必要的卫星图版权风险。

## 3. 研究与算法方案

### 3.1 数据预处理（离线 Python）
输入：一个或多个 `water` GeoParquet。
输出：`features-v1.bin/json`（轻量特征索引）、`metadata-v1.json`（地物信息）、`shapes/<id>.json` 或分块压缩的轮廓详情。

流程：
1. 读取列、过滤 subtype 和 Polygon/MultiPolygon。
2. 修复常见无效几何；保留重要外环。对于 MultiPolygon，需明确是拆为各部分还是整体保留；V1 推荐拆成独立候选并记录 `parent_id`，避免离散水面混成怪异形状。
3. 对每个候选使用局部投影把经纬度转换为米制平面坐标；勿直接把经纬度当欧氏 x/y，因为东西方向尺度取决于纬度。小范围可用局部等距投影，极区/跨 180° 经线需单独处理。
4. 记录面积、周长、bbox、代表性地图点、名称和源 ID；过滤空、多边形边界退化、极小或极大的数据，但保留筛选日志。
5. 外环简化和平滑应当克制；按弧长均匀采样 128 个点（可研究 64、256 的影响）。将中心平移到原点，按 RMS 半径缩放，得到归一化轮廓。
6. 预计算：低频傅里叶描述子（建议 12～24 维）、紧致度、长宽比、凹凸性等粗筛特征；保留 128 点标准化轮廓供精排。
7. 按类别、地域、复杂度统计分布，生成独立 `data_manifest.json`：来源、版本、过滤方式、结果数量、许可、处理脚本 commit。

**避免伪结果：** 每个前端候选通过 `id` 回指原始数据，并可核验经纬度及真实轮廓。

### 3.2 为什么要两级检索
- **粗筛（速度）：** 对草图计算傅里叶描述子、紧致度等低维特征，与所有候选进行距离比较，保留 Top 100～300。对 1～5 万候选可以先使用 NumPy 或浏览器 Web Worker 顺序计算；不急于加入 FAISS。
- **精排（效果）：** 将草图与候选的 128 点轮廓作尺度平移归一化，针对起点循环移位求最优旋转对齐，再计算平均边界距离；可尝试对称 Chamfer Distance、二值区域 IoU 作为辅助。
- **多样性重排：** 去掉同一个源地物重复部分、极近重叠多边形和大量几乎相同的候选，避免首页十个椭圆。

### 3.3 建议数学表达
将一个闭合轮廓按弧长采样为复数点列 `z_k = x_k + i y_k`，平移和缩放得到

`z'_k = (z_k - mean(z)) / sqrt(mean(|z_k - mean(z)|²))`。

粗筛特征可使用离散傅里叶变换 `Z_m = DFT(z')_m` 的若干低频幅值。幅值能降低平移、缩放、起点和旋转的影响，但会丢失部分结构，并可能无法区分镜像轮廓，因此只用于粗筛。

精排可以用循环偏移 `s` 与旋转角 `theta` 最小化

`D(A,B) = min_{s, theta} sqrt( (1/N) sum_k |a_k - exp(i theta) b_(k+s mod N)|² )`。

`theta` 可由两序列的复数相关计算，不必暴力遍历 360 个角度。逆序采样只改变走向，不等同于镜像；镜像匹配必须对坐标显式做反射（如复共轭），并由用户开关控制。

该指标假定点列沿对应轮廓保持相近的弧长结构，对严重形变不稳定；可以加对称 Chamfer 复核少量 Top 候选。Hu 矩 `cv2.matchShapes` 作为基准算法，未必是最终最优方案。

### 3.4 绘图输入的规范化
- 提供自由画笔与关闭后“自动闭合”；不能把明显开放曲线硬解释成可信的湖泊轮廓。
- 检测自交、极短曲线、面积接近零；提示重画，或提供清楚标注的自动修复选项。
- 支持撤销、清空、简单平滑、关闭/开启镜像；旋转匹配默认为开启。
- 圆形、椭圆等常见形状不能强行宣称“惊人相似”；呈现不同候选和区域过滤。
- V1 不提供多笔画汉字或线条简笔画搜索；将“不支持的图形种类”清楚写在界面提示。

### 3.5 查询与结果数据结构示例
```json
{
  "query": {
    "contour": [[0.1, 0.2], [0.4, 0.1], [0.7, 0.2]],
    "allowRotation": true,
    "allowMirror": false,
    "featureTypes": ["lake", "pond", "reservoir"],
    "region": "available-dataset"
  },
  "results": [
    {
      "id": "source-id:part-0",
      "sourceId": "original-water-feature-id",
      "name": null,
      "subtype": "lake",
      "location": {"lon": -89.5, "lat": 44.5},
      "score": 0.123,

```
上方数值是模式说明的**虚构示例**，不能当作已检索出的真实地物。`score` 作为内部排序代价，而非展示给用户的“98% 相似”。地图点应使用位于多边形内部的 representative point，不能默认质心必然在水体内。

### 4.2 建议技术栈
- 地理处理：Python 3.11+、GeoPandas、Shapely、PyProj、NumPy、DuckDB。
- 形状匹配基线：OpenCV Hu 矩、SciPy / NumPy 的傅里叶描述子与轮廓对齐。
- 页面：React + TypeScript + Vite。
- 绘图：原生 Canvas 或 react-konva。
- 地图：MapLibre GL JS + 明确允许使用的底图服务；保留可见署名。
- 浏览器检索：Web Worker + Float32Array；必要时增加 WebAssembly。
- 分享：URL 中编码简化草图与源 ID；导出 SVG/PNG，首版不依赖云存储。
- 测试：pytest（数据与算法）、Vitest（前端逻辑）、Playwright（端到端）。

**Qoder 部署注意：** 官方 Sites Free 版只保证静态部署；需在项目第一周验证使用 Qoder Sites 发布此类 React/Vite 静态项目的实际流程。不要假设任何本地仓库都一定可一键导入。若 Sites 的构建/发布流程不同，以官方支持的路径调整前端构建；比赛必须最终使用 Qoder Sites 的公网链接。

## 5. UI 交互与传播

### 5.1 首页
- 主标题：“画一个形状，去地球上找它”。
- 一张绘图画布 + 右侧搜索结果面板。
- 三个经过真实数据验证的可点击示例轮廓；不能使用伪造的地理结果。
- 轻量提示：“当前搜索湖泊、水库、池塘的外轮廓；暂不搜索文字、任意线稿和卫星影像纹理”。

### 5.2 搜索结果
- 每项：轮廓缩略图、地物类型、名称（如有）、地图位置、小型叠加图。
- 点击后地图定位、显示真实矢量边界、交互旋转和透明度调节。
- 在缺少名字时不要杜撰地名；显示坐标或附近区域（需要来源）。
- “附近地图/外部地图查看”仅进行正常地图导航，不自动爬取卫星图块。

### 5.3 分享卡片
- 画出的草图（左）、真实地物矢量轮廓（右）、位置、来源与站点名称。
- 文案可自选：“我在地球上找到了像这个图案的地方”。
- 生成 SVG / PNG，分享链接必须能重现同一检索查询或锁定具体结果。
- 优先不嵌入第三方底图图片，避免截图许可、加载失败等问题。

### 5.4 移动端体验
- 手指画线顺滑、笔迹独立于页面滚动；画布有清空/撤销。
- 结果列表在绘图画布下方；点开结果后地图占屏幕主要区域。
- 首次加载提供索引大小与加载进度；网络慢时展示经过真实数据制作的示例，但明确标示样例来源。

## 6. 关键实验设计：必须先做、再建站

### 6.1 验证 A：候选库可用性
- 从至少两个区域提取真实湖泊水库轮廓，记录原始数量、过滤后数量、按面积/复杂度的分布。
- 检查几十个随机候选与地图位置是否一一对应。
- 避免多边形切片、极小碎片、过度简化造成的假形状。
- 统计相似轮廓的重复情况，评估多样性。

### 6.2 验证 B：几何检索准确度
**合成测试：** 从候选库抽取 100～200 个真实轮廓，进行随机平移、缩放、旋转、轻微形变和重采样，作为模拟手绘查询；检查源对象能否位于 Top-1/Top-10。此测试主要验证实现正确性，不代表真人手绘效果。

**真实手绘测试：** 请几名普通用户各画几种不同的封闭轮廓，预先固定查询集；展示 Top-10 真实候选，由用户直接判断哪些肉眼明显相似、哪些具备惊喜感，并记录失败类型。不要在观测结果出来之后随意修改测试集。

**对照算法：** Hu 矩；傅里叶幅值；傅里叶粗筛 + 轮廓对齐精排。固定同一数据和查询，比较检索质量、耗时、重复结果比例。

### 6.3 验证 C：前端运行
- 以 1,000～5,000 个轮廓做首次打包；随后试 1～5 万规模。
- 验证桌面与手机浏览器的加载/检索速度；检索放 Web Worker 防止冻结页面。
- 记录压缩包大小、内存、结果延迟和地图首次加载；超出可接受范围先优化数据格式，不急于上服务器。

### 6.4 Go / No-Go 决策
在真实数据上使用至少 10 个不同的用户手绘轮廓测试：
- 若多数查询在前 10 个结果中能找到肉眼明显相似的真实地物，并且移动端端到端流程顺畅，继续开发。
- 若只能在自己提前挑好的几张图上成功，或大部分结果只是重复椭圆，则暂停 UI 投入，优先改数据覆盖和检索算法。
- 若纯几何无法形成吸引力，可向“地图轮廓拼图 / 地球形状探索”调整产品定位，而非夸大任意草图视觉检索的能力。

门槛是项目内部决策规则，不用于制造用户看不懂的评分指标。

## 8. Agent/Qoder 开发策略

### 8.1 协作原则
- 人决定问题范围和测试标准，Agent 写可验收的独立模块。
- 不允许 Agent 在无真实数据时用手工预设的“心形湖泊”结果充当检索实现。
- 先 PoC、后 UI；禁止未经允许接入付费 API、下载全球超大数据、重构已验证模块。
- 每个任务必须给：输入文件、预期输出、运行命令、测试样例、失败处理、改动清单。
- 保留 `experiments/results.csv`、基线结果和关键命令，避免模型换版本后无法重现。

### 8.2 可直接交给 Qoder / Codex 的首次技术任务

> 你是 EarthGlyph 项目的地理数据与几何检索工程师。请先**不要开发网页**。目标是在开放、可合法使用的真实水体轮廓上实现基线检索。优先使用 Overture Maps base/water 类型，严格依据官方当前 Schema；从一个小 bbox 下载 GeoParquet 并打印实际字段。筛选湖泊、水库、池塘的 Polygon/MultiPolygon，处理无效几何、投影、面积过滤、重采样，保留真实 ID、经纬度和来源。实现至少两种轮廓检索基线：Hu 矩 + 傅里叶描述子，并在相同草图上比较；输出 Top-10 候选的轮廓拼图及每个候选的真实地图定位信息。编写 pytest 单元测试，测试平移缩放旋转不变性、镜像开关、无效草图和重复水体过滤。**禁止**用合成湖泊或静态结果代替真实索引；若数据无法下载，明确报告阻塞并提供复现命令，不得伪造结果。交付 `scripts/prepare_polygons.py`、`scripts/build_index.py`、`scripts/evaluate_retrieval.py`、`experiments/results.csv`、`experiments/experiment_log.md`，最后用文字报告实际候选数量、耗时、失败案例、下一步行动。

### 8.3 前端阶段的 Agent 任务模板

> 在已有真实检索模块和经过校验的数据格式上，使用 React、TypeScript、Vite 实现 EarthGlyph 的网页 UI。左侧手绘画布，右侧真实检索候选；使用 MapLibre GL JS 展示候选地物坐标和真实矢量边界。搜索必须调用现有真实索引，不能使用任何虚构的展示结果。检索放到 Web Worker，页面移动端自适应，支持自动闭合、清空、撤销、旋转/镜像设置、结果叠加对比。保留所有地图数据署名。先完成可运行原型，再完善外观；每项功能都附测试与验收步骤。不得增加登录、排行榜、聊天或大模型调用。

### 8.4 Qoder Credits 控制
- 数据预处理与基础算法尽量用本地 Python 可复现脚本；大规模地理数据本身不传给 Qoder 对话上下文。
- 让 Agent 读取 `data_manifest.json`、真实样例和简短输出，而不是一次传入巨型 GeoJSON。
- UI 模块按组件分工，每次只让 Qoder 修改明确的若干文件；跑单测后再提交。
- 使用 Git 小步提交；保留可工作的“前端 + 真实数据”版本，避免一次性推翻。
- 站点访问/部署限制与开发 Credits 是两种独立资源；优先静态部署，降低访问成本。

## 9. 测试验收清单

**数据层**
- [ ] 全部结果能回查真实来源 ID、地理位置、数据版本。
- [ ] 名称不存在时不虚构；无效几何不会导致程序崩溃。
- [ ] 过滤掉 Point、LineString、海洋切片及不可视作单一轮廓的对象。
- [ ] 投影和归一化对不同纬度有合理处理。

**算法层**
- [ ] 固定草图复现实验结果。
- [ ] 旋转与尺度变换下，候选排序具有合理稳定性。
- [ ] 镜像关闭时不会把镜像匹配误解释为同一方向。
- [ ] 有完整的空结果/无效输入提示。
- [ ] 真实用户草图测试与失败样例保存。

**用户体验**
- [ ] 3 步内从打开页面到首个真实检索结果。
- [ ] 搜索过程页面不冻结；弱网下清楚显示正在加载。
- [ ] 每条结果能够定位到地图和真实轮廓。
- [ ] 手机可手绘、操作结果、放大地图。
- [ ] 共享链接和发现卡片能正确复原或标注草图与地点。

**发布**
- [ ] 公网 Qoder Sites 链接无登录门槛，评委可以直接体验。
- [ ] 地图与数据来源许可展示正确，不使用被禁止抓取的地图瓦片。
- [ ] 作品说明不夸大成“全球卫星影像任意搜索”。
- [ ] 网站包含数据覆盖与更新日期说明；有针对用户的基本隐私提示（草图不上传到外部服务器，若确实如此）。

## 10. 后续扩展方向（比赛后）

- **V1.5：** 加入岛屿、河流曲线、道路封闭环等不同几何索引；各类采用独立匹配模型与界面提示。
- **V2：** 面向多笔画图案，通过骨架化、图结构匹配检索道路/河流网络。
- **V3：** 使用获得明确许可的遥感图像、草图到遥感影像的跨模态模型，建立区域级真实视觉搜索；先测试 Earth on Canvas 等数据集，严格区分模型论文效果与真实全球检索效果。
- **数据扩大：** 优化索引文件、WASM 或服务端搜索，加入全球区域分区索引，持续检查结果质量。
